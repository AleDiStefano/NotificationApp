    Cómo leer esto. Las secciones siguen el camino de una petición HTTP: entra por el controller, baja al service, toca el repository y la base, y vuelve. Cada sección tiene tres partes: qué es, cómo está hecho acá (con el código real del repo) y por qué, casi siempre con un ejemplo de la vida real. Los recuadros verdes explican una decisión de diseño; los azules son ejemplos del mundo real; los rojos son la trampa que se evita.

    La regla de oro

    Cada capa habla solo con la de abajo y a través de tipos propios. El controller no sabe SQL; el service no sabe HTTP; la entidad no sabe JSON. Cuando eso se respeta, cambiar una pieza (de REST a mensajería, de Postgres a otra base, de Basic a JWT) no obliga a tocar las demás.

    Sección 01El punto de entrada y el contenedor de Spring

    Todo arranca en una clase con un main de tres líneas:

    @SpringBootApplication es tres anotaciones en una: @ComponentScan (buscá clases anotadas en este paquete y los de abajo), @EnableAutoConfiguration (mirá qué hay en el classpath y configurá lo obvio: si ves postgresql armá un DataSource, si ves spring-web levantá Tomcat en el 8080) y @Configuration (esta clase puede definir beans).

    Bean, contenedor e inyección de dependencias

    Un bean es un objeto que crea y administra Spring, no vos con new. Al arrancar, Spring construye un contenedor con todos los beans (los @RestController, @Service, @Repository, @Component, @Configuration) y resuelve quién necesita a quién. En este proyecto la inyección es siempre por constructor:

    Por qué por constructor y no @Autowired en el campo

    Los campos son final: el objeto nace completo o no nace. Las dependencias quedan explícitas en la firma (si el constructor tiene 8 parámetros, la clase hace demasiado y se nota). Y en un test unitario construís la clase con new pasando dobles de prueba, sin levantar Spring.

    Mundo real

    Hoy NotificationService guarda en base y listo. Mañana tiene que publicar un mensaje en RabbitMQ. Como el controller depende de la interfaz NotificationService, le inyectás otra implementación y el controller ni se entera. Eso es lo que compra la inyección de dependencias: poder cambiar el cableado sin abrir las clases que ya funcionan.

    Sección 02La arquitectura en capas

    El paquete com.alejandro.notificationapp está partido por responsabilidad, no por entidad:

    Por qué partir por capa

    Cada archivo tiene una sola razón para cambiar. Un bug de "devuelve 200 cuando debería 404" se arregla en el controller o el GlobalExceptionHandler, nunca en la query. Una query lenta se optimiza en el repository sin riesgo de romper una regla de negocio. El equipo puede tocar capas distintas sin pisarse.

    Sección 03Capa Model — las entidades JPA

    Dos entidades: User (quién recibe) y Notification (qué se manda). JPA es el estándar de Java para mapear objetos a tablas; Hibernate es la implementación que trae Spring Boot.

    Las decisiones, una por una

    ID como UUID generado

    @GeneratedValue(strategy = GenerationType.UUID): la clave la genera Hibernate, no una secuencia de la base.

    Mundo real

    Con IDs autoincrementales (1, 2, 3…) cualquiera que vea /api/users/42 deduce que tenés ~42 usuarios y prueba /api/users/43. Con UUID no hay nada que adivinar. Además, si mañana hay que fusionar datos de dos entornos o generar el ID en el cliente antes de guardarlo, con autoincremental chocan las claves.

    Enums guardados como texto

    @Enumerated(EnumType.STRING) guarda "EMAIL", no 0.

    La trampa que se evita

    El default de JPA es ORDINAL: guarda la posición del valor en el enum. El día que alguien agrega WHATSAPP entre EMAIL y SMS, todas las filas que decían "SMS" ahora significan "WHATSAPP". Silencioso e irreversible. Con STRING el orden del enum no importa.

    La relación al destinatario

    Muchas notificaciones apuntan a un usuario. En la tabla notifications hay una columna recipient_id con foreign key. fetch = LAZY significa "no traigas el usuario de la base hasta que alguien pida notification.getRecipient()".

    Por qué LAZY

    Con EAGER (el default en @ManyToOne), cada vez que traés una notificación se hace un JOIN a users aunque no lo necesites. Multiplicá eso por una lista de 100 y son 100 JOINs regalados. LAZY te obliga a decidir explícitamente cuándo querés el usuario — y ese "cuándo" acá es el mapper, todavía dentro de la transacción.

    Timestamps automáticos y tipo Instant

    @CreationTimestamp y @UpdateTimestamp (de Hibernate) llenan createdAt / updatedAt solos. Se usa Instant (un punto en la línea de tiempo UTC), no LocalDateTime.

    Mundo real

    LocalDateTime no tiene zona horaria: "2026-09-01 15:00" ¿de dónde? Si el server está en UTC y el dev en Buenos Aires, los logs y la base discrepan 3 horas y nadie sabe cuál es la verdad. Instant es siempre el mismo instante mundial; se convierte a la zona del usuario solo al mostrarlo.

    Constructor protected vacío + constructor "de verdad"

    JPA necesita un constructor sin argumentos para instanciar la entidad al leerla de la base (por eso está, pero protected para que el resto del código no lo use). El constructor público exige lo mínimo para que una Notification nazca en un estado válido: destinatario, asunto, mensaje y canal — y arranca en PENDING.

    Lógica en la entidad, no "objeto anémico"

    La regla "cuando pasa a SENT por primera vez, registrá sentAt" vive dentro de la entidad. El service llama notification.changeStatus(SENT) y no puede olvidarse de setear sentAt, porque no es su responsabilidad.

    Sección 04Capa Repository — Spring Data JPA

    Es una interfaz, sin implementación. Al arrancar, Spring Data genera en memoria una clase que la implementa. JpaRepository<User, UUID> ya trae save, findById, findAll(Pageable), delete, etc.

    Los métodos que agregamos se traducen por su nombre: existsByEmailIgnoreCase → SELECT count(*) > 0 FROM users WHERE lower(email) = lower(?). No se escribe SQL.

    Cuando el nombre no alcanza: @Query

    Es JPQL (consulta sobre entidades, no sobre tablas: Notification, no notifications). El truco :param is null or campo = :param hace que cada filtro sea opcional: si el controller no manda status, esa línea no filtra nada. Un solo método cubre "todas", "las de este usuario", "las fallidas de este usuario", etc.

    Paginación: Page y Pageable

    Ningún endpoint de listado devuelve una List pelada. Devuelven Page<T>: una porción (por defecto 20) más metadata (total, página actual, total de páginas).

    Mundo real

    Un findAll() sobre una tabla de dos millones de notificaciones trae dos millones de objetos a memoria y probablemente tira el proceso con OutOfMemoryError. Con Pageable, el SQL lleva LIMIT 20 OFFSET … y el response es chico y predecible. Es de esas cosas que hay que dejar bien desde el día uno porque después duele.

    Sección 05DTOs — por qué la API no expone las entidades

    Un DTO (Data Transfer Object) es el objeto que viaja por la API. Están en dto/, son record (inmutables, sin getters a mano) y hay uno de entrada y otro de salida:

    La trampa que se evita

    Si el endpoint devolviera la entidad User directamente, el JSON incluiría password (el hash). Y el día que alguien agregue passwordResetToken o failedLoginAttempts a la entidad, esos campos aparecen en la respuesta sin que nadie lo haya decidido. El DTO de salida es una lista blanca: solo sale lo que está escrito ahí.

    Por qué separar entrada de salida

    Lo que el cliente puede mandar y lo que la API devuelve no son lo mismo. En el alta, el cliente manda password pero no id ni createdAt (los pone el server). En la respuesta es al revés. Dos records distintos evitan campos "que a veces sí y a veces no".

    Mundo real

    Si la API expone la entidad, el contrato con el front queda pegado al esquema de la base. Renombrás una columna para una migración y rompés la app móvil que está en revisión de Apple hace una semana. Con DTOs, la base evoluciona por dentro y el contrato público cambia solo cuando vos querés.

    Sección 06Bean Validation — validar en el borde

    Las anotaciones @NotBlank, @Email, @Size, @NotNull sobre los campos del record son Jakarta Bean Validation. Se disparan cuando el controller marca el parámetro con @Valid:

    Si el body no cumple, Spring lanza MethodArgumentNotValidException antes de entrar al método, y el GlobalExceptionHandler (sección 10) la convierte en un 400 con la lista de campos que fallaron.

    Por qué acá y no en la base o en el service

    La base también rechazaría un email de 500 caracteres, pero con un error de constraint ilegible y un 500. Validar en el borde da un mensaje claro y accionable ("password: el tamaño debe estar entre 8 y 72") y le ahorra a las capas de abajo tener que desconfiar de sus entradas.

    Sección 07Mappers — la traducción entidad ↔ DTO

    La conversión vive en un solo lugar. Si mañana NotificationResponse tiene que ocultar el message para notificaciones de otro usuario, se cambia acá y vale para todos los endpoints. NotificationMapper compone UserMapper en vez de repetir la conversión del destinatario.

    Por qué una clase y no MapStruct

    Con dos entidades, un mapper a mano son 15 líneas legibles y sin magia. MapStruct (que genera el mapper en tiempo de compilación) empieza a valer la pena con 15 entidades y jerarquías anidadas. Meterlo ahora es complejidad sin retorno.

    Sección 08Capa Service — negocio y transacciones

    Cada service es una interfaz (NotificationService) más una implementación (NotificationServiceImpl). El controller depende de la interfaz.

    Qué es una transacción

    @Transactional envuelve el método en una transacción de base: o pasa todo, o no pasa nada. Si create encuentra al usuario, construye la notificación y falla al guardar, no queda nada a medias.

    Mundo real

    El ejemplo clásico es la transferencia bancaria: restar de una cuenta y sumar a otra tienen que ser atómicos. Acá el caso es más sutil pero igual de real: leer el usuario, validar reglas y escribir la notificación deben ver una foto consistente de la base y confirmarse juntos.

    Por qué readOnly = true en la clase

    La mayoría de los métodos solo leen. readOnly = true le avisa a Hibernate que no haga dirty checking (no compare cada objeto por si cambió) y al driver que puede optimizar. Los métodos que escriben (create, update, delete) ponen @Transactional a secas y ganan.

    Por qué saveAndFlush y no save

    save() solo agenda el INSERT; Hibernate recién genera createdAt / updatedAt al hacer flush, que por defecto ocurre al cerrar la transacción. Como el mapeo a DTO pasa antes de ese cierre, los timestamps salían en null en la respuesta del alta. saveAndFlush() fuerza el flush dentro del método: el objeto ya tiene los valores cuando lo mapeamos.

    El patrón findOrThrow

    findById devuelve Optional<Notification>. En vez de repetir el .orElseThrow(...) en cada método, hay un helper privado. Lanza ResourceNotFoundException, que la capa de errores convierte en 404. El service no sabe que existe el número 404 — solo dice "esto no está".

    Sección 09Capa Controller — hablar HTTP bien

    El controller no tiene lógica: recibe, delega en el service, elige el código HTTP y devuelve. Cada verbo tiene una semántica que conviene respetar:

    VerboUso acáIdempotenteÉxito
    POSTcrearNo — dos POST = dos recursos201 Created + Location
    GETleerSí — no cambia nada200 OK
    PUTreemplazar el user completoSí — repetirlo deja el mismo estado200 OK
    PATCHcambiar solo el estadoSí (en este caso)200 OK
    DELETEborrarSí — borrar dos veces = borrado204 No Content
    Mundo real — por qué 201 y el header Location

    Un cliente hace POST /api/notifications. Con 201 sabe que se creó (no solo que "salió bien"), y el header Location: /api/notifications/b25e… le dice exactamente dónde quedó, sin tener que parsear el body ni adivinar la URL. Un webhook o un script de integración se apoyan en eso.

    Mundo real — por qué importa la idempotencia

    La app móvil manda DELETE /api/notifications/123, el celular pierde señal, no llega la respuesta, y reintenta. Con DELETE idempotente el segundo intento devuelve 204 igual y no pasa nada raro. Si "borrar" estuviera en un POST que además incrementa un contador, el reintento lo rompe.

    El listado usa @PageableDefault: ?page=0&size=20&sort=createdAt,desc sale gratis, y los filtros son @RequestParam(required = false) — opcionales, como la query del repository.

    Sección 10Manejo de errores centralizado

    Ni un try/catch en los controllers. Una sola clase con @RestControllerAdvice intercepta las excepciones de todas las capas y las convierte en el mismo formato de error:

    ExcepciónHTTPCuándo
    ResourceNotFoundException404el id no existe
    DuplicateResourceException409email ya registrado
    MethodArgumentNotValidException400body inválido (con lista de campos)
    MethodArgumentTypeMismatchException400/api/users/abc — "abc" no es UUID
    HttpMessageNotReadableException400JSON roto o enum inexistente ("channel":"CARTA")
    DataIntegrityViolationException409borrar un user con notificaciones (FK)
    Exception (catch-all)500cualquier otra — se logea completa, se devuelve genérica
    La trampa que se evita

    El handler de Exception logea el stacktrace del lado del server pero al cliente le manda "Ocurrió un error inesperado". Nunca un stacktrace en el response: filtra nombres de clases, versiones, rutas de archivos y a veces fragmentos de query — un mapa para un atacante.

    Por qué un formato único

    El front escribe un parser de errores: mira fieldErrors para pintar los campos del formulario en rojo, y message para el toast. Si cada endpoint devolviera errores con forma distinta, el manejo de errores del cliente sería un árbol de if infinito.

    Sección 11Seguridad — Spring Security

    Spring Security se mete como una cadena de filtros delante de los controllers: cada request pasa por autenticación y autorización antes de llegar al código. La config vive en config/SecurityConfig.java:

    BCrypt para las contraseñas

    El service nunca guarda la contraseña en claro: passwordEncoder.encode(raw) produce un hash BCrypt (con salt incluido y un costo configurable que lo hace deliberadamente lento).

    Mundo real

    Se filtra la base — pasa todo el tiempo. Con SHA-256 pelado, un atacante prueba millones de contraseñas por segundo contra el dump y saca las fáciles en minutos. BCrypt con costo 10 hace ~10 hashes por segundo por core: el mismo ataque pasa de minutos a años. El salt por usuario impide además las rainbow tables.

    Stateless: sin sesión en el server

    SessionCreationPolicy.STATELESS: el server no guarda una HttpSession. Cada request se autentica sola (hoy con HTTP Basic, mañana con un JWT en el header Authorization).

    Mundo real

    En producción corren 4 instancias detrás de un balanceador. Con sesión en memoria, el usuario que se logueó en la instancia 2 explota si la request siguiente cae en la 3 (o necesitás sticky sessions y un Redis compartido). Sin estado, cualquier instancia atiende cualquier request y escalar es agregar réplicas.

    CSRF deshabilitado — y por qué acá está bien

    El razonamiento

    CSRF protege contra que el navegador adjunte credenciales ambientales (una cookie de sesión) en una request forjada desde otro sitio. Una API stateless que se autentica con un token en el header Authorization no tiene ese vector: otro origen no puede leer ni setear ese header. Si esta API usara cookies de sesión + browser, CSRF tendría que quedar activo.

    Hoy HTTP Basic, mañana JWT

    Por ahora hay un único usuario administrador en memoria (UserDetailsService con app.admin.*) y se entra con HTTP Basic (admin / admin). El .env.example ya reserva JWT_SECRET y JWT_EXPIRATION_MS: el próximo paso es un UserDetailsService que lea de UserRepository (findByEmailIgnoreCase ya está) y un filtro que valide el token JWT — se enchufa en esta misma cadena, antes de UsernamePasswordAuthenticationFilter.

    Sección 12RabbitMQ — mensajería asíncrona

    RabbitMQ es un message broker: un intermediario donde un proceso deja un mensaje y otro lo levanta cuando puede. El vocabulario:

    TérminoQué es
    Producerquien publica el mensaje (acá: la API, al crear la notificación)
    Exchangela "central de correo": recibe el mensaje y decide a qué cola(s) va
    Routing keyla etiqueta del mensaje (p. ej. notification.email) que el exchange usa para enrutar
    Queuela cola donde el mensaje espera hasta ser consumido
    Consumer / workerel proceso que saca mensajes de la cola y hace el trabajo (llamar a SendGrid, a Twilio…)
    Ackel consumer confirma "procesado"; sin ack, RabbitMQ re-entrega el mensaje

    Por qué asíncrono y no mandar el email en el mismo request

    Mundo real — el pico de Black Friday

    A las 00:00 se disparan 80.000 notificaciones "tu pedido fue confirmado". Si cada POST esperara a que SendGrid responda (200–800 ms cada uno), los threads de Tomcat se agotan, la API deja de responder todo — incluido el login — y el pico se transforma en caída. Con la cola, la API solo escribe una fila y publica un mensaje (~milisegundos); los workers drenan la cola a su ritmo. La cola amortigua el pico.

    Mundo real — el proveedor se cae

    Twilio tiene un incidente de 15 minutos. Sin cola, esos 15 minutos de SMS se pierden (o cada request devuelve error y el usuario lo ve). Con cola, los mensajes se acumulan; cuando Twilio vuelve, el worker los procesa. Sumás una dead-letter queue para los que fallan N veces y tenés reintentos y una bandeja de "revisar a mano" sin escribir un scheduler.

    Por qué desacoplar

    El código que atiende el POST no necesita saber cómo se manda un email. Publica "hay que notificar a este usuario por EMAIL" y sigue. El worker de email, el de SMS y el de push evolucionan, se despliegan y escalan por separado. Incluso podés tener varios workers compitiendo por la misma cola para ir más rápido.

    Cómo encaja en este código hoy

    La dependencia spring-boot-starter-amqp ya está en el pom.xml y Testcontainers ya levanta un RabbitMQ para los tests. El modelo lo anticipa: el estado PENDING → SENT / FAILED de Notification es exactamente el ciclo de vida de un mensaje en la cola. Falta la pieza del medio: al crear la notificación, publicar el mensaje (RabbitTemplate.convertAndSend(...)); y un @RabbitListener que consuma, llame al proveedor y haga notification.changeStatus(SENT).

    Sección 13Actuator — la app se cuenta a sí misma

    Spring Boot Actuator expone endpoints operativos bajo /actuator. En este proyecto, solo dos:

    • GET /actuator/health → {"status":"UP"} si la app y sus dependencias (la base) responden; DOWN + 503 si no.
    • GET /actuator/info → metadata de build (versión, commit) si se configura.
    Mundo real — Kubernetes

    K8s hace dos chequeos periódicos: liveness ("¿está vivo? si no, reiniciá el pod") y readiness ("¿puede recibir tráfico? si no, sacalo del balanceador"). Ambos pegan a /actuator/health. Si la conexión a Postgres se cae, health devuelve 503, K8s deja de mandarle tráfico a ese pod, y cuando la base vuelve el pod se reincorpora solo. Sin este endpoint, K8s manda usuarios a una instancia rota.

    Mundo real — monitoreo

    Agregando micrometer-registry-prometheus aparece /actuator/prometheus con métricas (requests por segundo, latencia p99, uso del pool de conexiones, memoria de la JVM). Prometheus las scrapea cada 15 s y Grafana las grafica. Es la diferencia entre "un usuario dice que anda lento" y "la latencia p99 saltó a las 14:32, justo con el deploy".

    La trampa que se evita

    exposure.include es una lista blanca a propósito. Actuator también puede exponer /actuator/env (todas las variables de entorno, incluidos secretos), /actuator/heapdump (un volcado de memoria descargable) y /actuator/loggers (cambiar niveles de log en caliente). Exponer * a internet es regalar la llave.

    Por qué management.health.rabbit.enabled=false

    El starter de AMQP trae un health indicator para RabbitMQ. Como todavía no hay un broker en desarrollo, ese indicador daría DOWN y arrastraría el health global a DOWN — y entonces un K8s real no dejaría arrancar la app. Se apaga hasta que RabbitMQ sea de verdad una dependencia.

    Sección 14Testcontainers — tests con infra real

    Al correr los tests, Testcontainers arranca un PostgreSQL y un RabbitMQ reales en Docker, efímeros, y @ServiceConnection inyecta sus URLs/credenciales en el contexto de Spring automáticamente. Al terminar, los contenedores se destruyen.

    La trampa que se evita — "en mi máquina con H2 pasaba"

    La tentación es testear contra H2 (una base en memoria). Pero H2 no es PostgreSQL: los tipos, las funciones (ILIKE, JSONB, ON CONFLICT), el comportamiento de las secuencias y hasta los mensajes de error de constraint son distintos. Un test que pasa con H2 y una feature que explota en producción es el clásico "pero los tests estaban verdes".

    Por qué también sirve para desarrollar

    ./mvnw spring-boot:test-run levanta la app usando esta config: un dev clona el repo, tiene Docker, y corre la app completa con su base y su broker sin instalar ni configurar nada. El docker-compose.yml queda para quien prefiera una base persistente entre reinicios.

    Sección 15OpenAPI / Swagger — el contrato vivo

    springdoc-openapi escanea los controllers, los DTOs y sus anotaciones de validación en tiempo de arranque y arma el documento OpenAPI 3 en /v3/api-docs. Swagger UI (en /swagger-ui.html) lo pinta como una consola donde probar cada endpoint. El SecurityScheme hace que el botón Authorize pida usuario/contraseña y los mande en cada llamada.

    Por qué generado y no escrito a mano

    Un README con ejemplos de curl se desactualiza en la primera semana. Este documento sale del código: si agregás un campo al DTO o un endpoint, la doc cambia sola. El front puede incluso generar su cliente HTTP desde el /v3/api-docs.

    Sección 16Configuración y entornos

    ${VAR:default}

    Toma la variable de entorno VAR; si no está, usa el default. En local funciona sin configurar nada; en producción el operador setea DATABASE_URL, DATABASE_PASSWORD, etc. El .env.example documenta qué variables existen; el .env real (con los secretos) está en .gitignore.

    Mundo real

    Una contraseña de base commiteada al repo queda para siempre en el historial de git, aunque después la borres. Los secretos van por variable de entorno (o Vault, o los secrets de K8s), nunca en un archivo versionado.

    ddl-auto=update

    Hibernate ajusta el esquema al arrancar comparándolo con las entidades. Cómodo en desarrollo.

    La trampa que se evita

    update nunca borra ni cambia una columna existente, y no es reproducible. En producción se usa Flyway o Liquibase: migraciones versionadas (V1__crear_users.sql, V2__agregar_indice.sql) que se aplican en orden, quedan en git y corren igual en cada entorno. Está anotado como pendiente.

    open-in-view=false

    Por qué apagarlo

    Con Open Session In View (el default de Spring Boot), la sesión de Hibernate queda abierta hasta que termina de renderizarse la respuesta, así que un getRecipient() lazy en el mapper "funciona" — disparando queries sueltas fuera de toda transacción, el terreno del problema N+1. Apagándolo, si el código accede a algo lazy fuera de la transacción, falla en los tests y te obliga a cargar por adelantado lo que la respuesta necesita. Por eso el mapeo a DTO se hace dentro del método @Transactional del service.

    Sección 17El pom.xml

    El <parent> es spring-boot-starter-parent: un BOM (Bill of Materials) que fija versiones compatibles de cientos de librerías, así no hay que elegirlas a mano. Las dependencias son starters — paquetes temáticos:

    StarterQué traeEstado
    data-jpaJPA, Hibernate, pool de conexiones HikariCPen uso
    web (vía websocket)Spring MVC, Tomcat embebido, Jacksonen uso
    securityla cadena de filtros, BCrypten uso
    validationJakarta Bean Validation (Hibernate Validator)en uso
    actuator/health, /info, métricasen uso
    amqpcliente RabbitMQ, RabbitTemplate, @RabbitListenerlisto, sin cablear
    mailJavaMailSenderlisto, para el worker de email
    websocketSTOMP/SockJSlisto, para push in-app
    springdoc-openapiOpenAPI 3 + Swagger UI (v3.1.0, la línea que soporta Boot 4)en uso

    Detalles que valen: postgresql tiene <scope>runtime</scope> (el código compila contra JDBC, no contra el driver); lombok y devtools son <optional>true</optional> (no se propagan a quien use este artefacto, y devtools se desactiva solo al correr desde el jar); los testcontainers-* son <scope>test</scope>. Lombok está disponible pero las entidades usan getters explícitos a propósito — son parte del contrato de dominio y conviene verlos.

    Sección 20Glosario

    Beanobjeto creado y administrado por el contenedor de Spring
    IoC / DIinversión de control / inyección de dependencias: las clases reciben sus colaboradores en vez de crearlos
    ORMmapeo objeto-relacional: objetos Java ↔ filas de tablas (JPA es el estándar, Hibernate la implementación)
    JPQLlenguaje de consultas de JPA, escrito sobre entidades y no sobre tablas
    DTOobjeto que viaja por la API; desacopla el contrato público del modelo interno
    Idempotenteejecutar la operación una o N veces deja el mismo estado
    Transacciónunidad atómica contra la base: confirma todo o revierte todo
    Brokerintermediario de mensajería (RabbitMQ); desacopla productor y consumidor en el tiempo
    Exchange / Queueel exchange enruta; la queue almacena hasta que un consumer procesa
    Dead-letter queuecola a donde van los mensajes que fallaron demasiadas veces
    Hash / salthuella irreversible de la contraseña; el salt (aleatorio por usuario) impide precomputar ataques
    BOMBill of Materials: POM que fija versiones compatibles de un set de librerías
    Starterdependencia "paraguas" de Spring Boot que trae todo lo necesario para un tema
    Dialectla variante de SQL que Hibernate genera para un motor concreto (Postgres ≠ H2 ≠ MySQL)
    OSIVOpen Session In View: mantiene la sesión de Hibernate abierta durante el render; acá está apagado
